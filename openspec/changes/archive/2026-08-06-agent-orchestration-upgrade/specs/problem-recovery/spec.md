## ADDED Requirements

### Requirement: 失败分类

系统 SHALL 对流程中的失败进行分类:LLM 调用错误、输出格式非法、编译失败、内容跑偏、前后矛盾、多次无收敛;分类结果作为恢复策略选择的依据,并记录到问题记录。

#### Scenario: 跑偏分类

- **WHEN** 某节点产物与用户需求存在整体性偏离
- **THEN** 失败被分类为内容跑偏,记录根因描述,选择对应的恢复策略

#### Scenario: 格式非法分类

- **WHEN** 节点输出无法通过其输出契约校验(如 Spec JSON 解析失败)
- **THEN** 失败被分类为输出格式非法,携带校验错误信息进入恢复流程

### Requirement: 恢复策略阶梯

Manager SHALL 按阶梯选择恢复策略:重派(带反馈回同一 worker)→ 拆分(并行派发子任务)→ 回退(更早节点)→ 上报(转人工);阶梯选择基于失败分类与诊断结论。

#### Scenario: 重派

- **WHEN** 方案设计节点产物与 PRD 不一致且缺口明确
- **THEN** Manager 携带缺失清单重派方案设计 worker,不重建全流程

#### Scenario: 拆分

- **WHEN** 功能实现节点失败源于多个模块互相依赖出错
- **THEN** Manager 将修复拆分为并行子任务,分别派发到对应 worker 实例

#### Scenario: 回退

- **WHEN** 失败根因指向更早节点的决策错误(如设计不满足需求)
- **THEN** Manager 回退到对应更早节点重新生成,并携带失败证据

#### Scenario: 上报

- **WHEN** 阶梯前三级均无法闭环
- **THEN** Manager 停止自主处理,向用户输出求援消息与"继续自主/转人工"选项

### Requirement: 自主闭环红线

Manager 的自主闭环 SHALL 遵守红线:每个问题自主处理不超过 2 轮,之后必须向用户汇报并提供接管选项;不得自主修改需求范围,范围变更必须经用户确认。

#### Scenario: 两轮后汇报

- **WHEN** 同一问题自主重试 2 轮仍未通过
- **THEN** Manager 输出 diagnosis_card(诊断、已尝试动作、建议),等待用户选择继续或接管

#### Scenario: 范围变更需确认

- **WHEN** 诊断结论建议删减某功能范围才能闭环
- **THEN** Manager 输出 confirm_card 请求用户确认,不得自行删减

### Requirement: 回退次数控制

系统 SHALL 沿用并扩展循环控制:每节点回退不超过 3 次、全局回退总数不超过 10 次、连续回退无改进时触发熔断转求援。

#### Scenario: 单节点回退超限

- **WHEN** 某节点回退次数达到 3 次
- **THEN** 系统禁止继续回退该节点,转求援流程

#### Scenario: 无改进熔断

- **WHEN** 连续两次回退到同一节点且输入哈希一致
- **THEN** 系统判定无改进,熔断并转求援

### Requirement: 问题记录持久化

每次失败诊断与修复闭环 SHALL 持久化到应用记忆的 problems.jsonl,包含问题描述、分类、根因、修复策略与结果;增量开发时作为已知问题与修复策略的检索来源。

#### Scenario: 问题记录写入

- **WHEN** 一次失败经修复闭环
- **THEN** problems.jsonl 追加完整记录(问题/分类/根因/修复/结果)

#### Scenario: 历史策略复用

- **WHEN** 增量开发中出现与历史记录同类的失败
- **THEN** Manager 检索并参考历史修复策略作为重派反馈的一部分
